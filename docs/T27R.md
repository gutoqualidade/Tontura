# TENERURA — Fase 7: a linguagem T27R (um subconjunto de Rust)

Data: 2026-11-17 · sessão autônoma, executada **em cópia**
(`~/tenerura-sandbox/`); `~/tenerura/` não foi tocado. Documentos vizinhos:
`07` (ISA), `08` (núcleo), `10` (Fase 6), `ESTADO.md`.

## A. O pedido, e o que ele não pode significar

Pedido: "queria que o TENERURA fosse em Rust". Tomado ao pé da letra,
"em Rust" quer dizer `rustc`, e isso não existe para esta máquina:

| caminho | por que não |
|---|---|
| `rustc` com alvo próprio | o `rustc` só emite LLVM IR; um alvo novo exige um backend LLVM para 27 trits, e a LLVM não tem (nem aceita) aritmética ternária balanceada. Escrever esse backend é maior que o TENERURA inteiro. |
| transpilar Rust → C → LLVM | o `clang` não está instalado e não há alvo ternário no C. O caminho `llvm-bootstrap/` existente só cobre um recorte escrito à mão (`.ll` versionados, não gerados). |
| rodar Rust binário sobre um emulador de 2 estados | trairia a decisão da Fase 1: a arquitetura é ternária **na semântica**, não só na representação. |
| embutir um interpretador Rust | não resolve nada: a linguagem continuaria sendo hospedeira, e o programa não viraria instruções T27. |

O que **pode** ser feito, e foi feito: uma linguagem com a sintaxe e as
ideias de Rust — `fn`, `let`/`let mut`, `if`/`else`, `while`, `match`,
imutabilidade por padrão, um único tipo de valor — compilada por um front
end próprio para assembly T27. Ela se chama **T27R**, arquivos `.t27r`,
compilador `t27r`. Não é Rust; é o subconjunto que a máquina consegue
honrar sem mentir.

Regra de honestidade adotada: **nada no compilador finge ser Rust.** Não há
`struct`, `enum`, `Option`, `Result`, trait, `&`, `&mut`, array nem string.
O que não existe dá erro de compilação, não um comportamento silencioso
diferente.

## B. O subconjunto

```text
programa  := item*
item      := 'fn' nome '(' params? ')' ('->' 'word')? bloco
params    := nome ':' 'word' (',' nome ':' 'word')*
bloco     := '{' comando* '}'
comando   := 'let' 'mut'? nome (':' 'word')? '=' expr ';'
           | nome '=' expr ';'
           | 'if' expr bloco ('else' (bloco | 'if' ...))?
           | 'while' expr bloco
           | 'return' expr? ';'
           | 'match' expr '{' braço* '}'
           | expr ';'
braço     := padrao ('|' padrao)* '=>' bloco
padrao    := '-'? número | '_'
expr      := or ; or := and ('||' and)* ; and := cmp ('&&' cmp)*
cmp       := soma (('=='|'!='|'<'|'<='|'>'|'>=') soma)*
soma      := termo (('+'|'-') termo)*
termo     := unário (('*'|'/'|'%') unário)*
unário    := ('-'|'!') unário | primário
primário  := número | 'true' | 'false' | nome | chamada | '(' expr ')'
```

Um único tipo: `word`, a palavra de 27 trits (faixa ±3 812 798 742 092 906).
`true` é `1`, `false` é `0`; qualquer valor não nulo é verdadeiro (a
máquina não tem tipo booleano separado). Comentários `//` até o fim da
linha. Sem literais de caractere: `putc(10)` em vez de `putc('\n')` — não
há tipo `char`, e inventar um seria mentir sobre o modelo de memória.

### Checagem estática (o "sabor Rust")

Tudo abaixo é recusado **antes** de gerar código, com linha e coluna:

- atribuição a variável não declarada `let mut` — imutável por padrão,
  como em Rust;
- nome inexistente, fora de escopo, ou usado antes da declaração;
- função inexistente, aridade errada, mais de 9 parâmetros (limite `a1..a9`);
- `main` ausente ou com parâmetros; função definida duas vezes; parâmetro
  repetido;
- `match` sem `_` — sobre uma palavra de 27 trits não há como enumerar os
  casos, então a exaustividade é exigida como `_` explícito; padrão
  repetido no mesmo `match` também é erro;
- literal fora da faixa de 27 trits;
- `exit(...)` usado como valor — ele não retorna, então só vale como
  comando. É o primeiro caso de uma regra de "tipo de retorno vazio" que
  ainda não generaliza para funções de usuário.

### Embutidas

| nome | aridade | o que é |
|---|---|---|
| `putc(x)` | 1 | escreve um caractere no console de depuração |
| `putdec(x)` | 1 | imprime `x` em decimal com sinal (rotina `putdec` de `ulib.inc`) |
| `exit(x)` | 1 | encerra a tarefa com código `x`; não retorna |
| `yield()` | 0 | `SYS_YIELD` |
| `time()` | 0 | `SYS_TIME` (relógio modular) |
| `recv(cap, paciência)` | 2 | `SYS_RECV`; devolve o estado (`a1`) |
| `recv_val(cap, paciência)` | 2 | `SYS_RECV` de uma mensagem de uma palavra: devolve `a3` (ou o estado, se não for `+1`) |
| `sign(x)` | 1 | `sgn` da ALU: −1 / 0 / +1 — o trit que o ternário tem de graça |
| `call(cap, op, valor)` | 3 | `SYS_CALL` com protocolo `(op, valor) → valor`; devolve a primeira palavra da resposta, ou o estado se não for `+1` |

`call` e `recv_val` são a ponte com o mundo em assembly: é assim que um
programa T27R conversa com um servidor escrito à mão, sem precisar de
structs. O protocolo visível é o mesmo dos programas de exemplo —
`call(cap, op, valor)` para pedido/resposta de duas palavras e
`recv_val(cap, paciência)` para mensagens de uma palavra. Mensagens de
várias palavras exigem `struct` (ou um par de capacidades), que ainda não
existe.

## C. Geração de código

Modelo de máquina de pilha, deliberadamente o mais simples que é correto:
toda expressão deixa o resultado em `a1`; binárias empilham o operando
esquerdo e desempilham em `t1`. Não há alocação de registradores nem
otimização — o objetivo é rastreabilidade: dá para ler o `.tas` gerado e
conferir contra a fonte, linha a linha.

Quadro de função:

```text
fn_x:
    push lr            ; retorno
    push s11           ; quadro anterior
    mov  s11, sp       ; base do quadro
    addi sp, sp, -N    ; N = locais (let) + parâmetros
    st a1, -1(s11)     ; parâmetros, na ordem em que o chamador passou
    ...
.Lret_x:
    mov sp, s11
    pop s11
    pop lr
    ret
```

- Locais em `s11-1 .. s11-N`; o corpo é gerado **antes** do prólogo para
  que `N` seja conhecido (uma passada, sem tabela de símbolos separada).
- Chamada de usuário: avalia argumentos da esquerda para a direita,
  empilhando; desempilha em `a1..a9` na ordem inversa; `call fn_nome`.
- Comparações usam `cmp` (que devolve o sinal da diferença) mais um desvio
  ternário: `==`→`bnz`, `!=`→`bz`, `<`→`bnn`, `<=`→`bp`, `>`→`bnp`,
  `>=`→`bn`. É a ALU auditada da Fase 4A, sem reinterpretação.
- `&&` e `||` curto-circuitam (dois desvios para o mesmo rótulo), e o
  resultado é normalizado em `0`/`1`.
- `!x` é `(x == 0)`, não complemento de bits: não há bits.
- Literais que não cabem em imediato de 16 trits usam `la` (dois passos,
  divisão pura de dígitos).
- `_start` chama `fn_main`, move o resultado para `a2` e salta para `exit`.

O `.tas` gerado inclui `../lib/abi.inc` e `../lib/ulib.inc`; por isso o
arquivo tem de morar em `src/os/user/` (ou em qualquer diretório com um
`../lib` ao lado). Uso:

```sh
tools/t27r.sh programa.t27r            # escreve programa.tas (via nix-shell)
t27r programa.t27r -o saida.tas
t27r -                                 # lê a entrada padrão, escreve na saída
```

ambas as tarefas saem com código 0. É o teste de aceitação da linguagem:

## E. O que falta, e por que falta

| falta | por que ainda não |
|---|---|
| `struct`, `enum` | exigem memória com tamanho composto e um modelo de layout; a pilha de uma tarefa tem 729 palavras, e sem `struct` não há como errar o layout |
| `Option`/`Result` | sem `enum` não há como defini-los; e o `Result` ternário natural (`−1`/`0`/`+1`) já está em `call`/`recv` como estado |
| traits, genéricos | não há monomorfização nem despacho; o custo não se paga num sistema de 5 programas |
| `&`, `&mut`, borrowing, lifetimes | são análises de front end (a LLVM não as vê; só `noalias`); fazem sentido quando existir heap ou memória compartilhada — hoje não existe nenhum dos dois |
| arrays, strings | sem `struct` e sem alocador, um array é só uma região da pilha; strings como literais exigem uma seção de dados por programa, que o formato `.tas` já suporta (`.stringz`), mas a linguagem ainda não emite |
| módulos, `use` | um arquivo = um programa; a granularidade ainda não dói |
| funções que "não retornam" em geral | só `exit` é reconhecido como divergente |
| otimização | nenhuma; o gerador é o mais ingênuo que é correto |

## F. O que o ternário muda em relação a Rust

Três pontos em que a máquina não é "Rust com outro inteiro":

1. **`match` de três vias é o `if` natural.** `sign(x)` devolve o trit, e
   `match sign(x) { -1 => …, 0 => …, _ => … }` cobre a reta inteira sem
   comparações encadeadas. Em Rust isso é `x.cmp(&0)` com três braços; aqui
   é uma instrução (`sgn`) e um salto.
2. **`Result` cabe num trit.** O estado de retorno do núcleo já é
   `−1`/`0`/`+1` (erro / nada / ok). Um `Result` ternário não precisa de
   discriminante separado do valor de erro: o sinal **é** o discriminante.
   `call`/`recv` expõem isso hoje como número; quando houver `enum`, o
   mapeamento é direto.
3. **Capacidade é valor linear, e o custo é o `move`.** `SYS_CAP_GRANT`
   (Fase 6) move autoridade entre tarefas; não copia. Em Rust, um
   `Cap<T>` linear (sem `Clone`) modela isso no front end; aqui o
   compilador ainda não tem tipos, então a linearidade é garantida pelo
   núcleo (I12), não pela linguagem.

E um ponto em que o TENERURA tem algo que Rust não tem: **tempo de vida
dinâmico**. Um `Cap` para tarefa carrega a geração; quando a tarefa morre e
a geração avança, a capacidade fica pendurada e o núcleo recusa. Rust
garante tempo de vida em compilação; aqui há também a garantia em execução,
que é o que um sistema com reinício de serviço precisa.

## G. Como estender (a ordem que faz sentido)

1. **strings e `puts`**: emitir `.stringz` e uma tabela por programa; é o
   que mais falta para os programas ficarem legíveis (`pingr.t27r` escreve
   a etiqueta com 11 `putc`).
2. **`enum` de um campo** (só `word`), o suficiente para `Result` e para
   estados nomeados; sem layout composto ainda.
3. **`struct` de campos `word`** com layout fixo na pilha; aí arrays de
   `word` saem quase de graça.
4. **retorno vazio generalizado** (`fn f() { … }` sem `-> word`), para
   escrever drivers sem `return 0` cerimonial.
5. **tipos de capacidade no front end** (`Cap<Send>`, `Cap<Recv>`) para
   que a linearidade seja checada antes do núcleo, e não só por ele.

Nada disso muda o núcleo: a linguagem é um front end, e o contrato com o
sistema continua sendo a ABI de `abi.inc` e a tabela de chamadas de
`docs/08`.

## H. Limites desta fase

- O compilador não tem testes de propriedade nem *fuzzing*: 16 testes
  dirigidos. Um gerador aleatório de programas T27R, comparando com um
  interpretador de referência, é o próximo passo natural de confiança.
- Não há verificação formal da geração de código; a garantia é
  diferencial (fonte → execução) e a leitura do `.tas`.
- O `.tas` gerado depende de `../lib`: não é autocontido.
- O código gerado é grande por construção (pilha, sem registradores), mas
  o custo total medido no mesmo trabalho (`ping`+`pong` isolados) é
  praticamente igual: **33 829** passos na versão T27R contra **34 046** na
  versão assembly (953 vs 426 instruções de usuário; o núcleo domina os
  dois). Ou seja: o gerador é ingênuo, não é o gargalo.
- `match` só compara literais; não há padrões de intervalo nem vínculo de
  nomes.
